# Modern Business Language (MBL) - Complete Design Document

## Overview

The programming languages used for business applications, integrations,
migrations, and reporting have never been very well suited to the task.  They
have never directly addressed the specific idealized needs for these tasks.
Above all, the ideal programming language for business would be intuitively
readable and modifiable with minimal work necessary by the programmer.  It
would also be robust and perform well.  To be this, the language requires the
following:

- Support for complex and versatile data structures.
- A rich and versatile date/time data type and expressions.
- A rich and versatile money data type and expressions.
- Versatile file I/O, text parsing, and text manipulation.
- Robust error handling and self-healing.
- Scheduled/triggered events.
- RESTful Services (provision and consumption).
- Websocket I/O for real-time interfaces.
- Authentication support via common authentication servers (e.g. AD, OpenID,
etc.)
- Encryption/Decryption Support.

This document describes a new language to meet these needs, called Modern
Business Language (MBL).

The vision is to provide a low learning curve so that knowledge workers with
business knowledge can understand and/or adapt automations that facilitate
business.  For example, an application for Loan Origination (in the finance
industry) or a Contract Management system (in the healthcare industry), or a
Physician Scheduling application (again, in the healthcare industry).  The
industry itself can vary.  Other examples include data integrations via web
APIs or files transferred via sFTP.

## Architecture

An MBL program may be either a tool or a server.  A tool runs from start to
finish to complete a task as where a server runs continually until stopped.

So every MBL program has its root function as either of type tool or server.

### Execution Model

Each MBL server or tool operates in a single-threaded environment, similar to
JavaScript's event loop model. This design choice eliminates the complexity of
async programming and threading issues, making business logic easier to
understand and debug.

**For Tools:**
- Execute sequentially from start to finish
- No concurrent operations within the tool itself
- External I/O operations are synchronous and blocking

**For Servers:**
- Run continuously in a single-threaded event loop
- Web service requests are buffered and processed sequentially
- Triggers and constraints are evaluated in deterministic order
- Each request is processed completely before the next begins

This approach prioritizes simplicity and predictability over raw performance,
which aligns with typical business application requirements where correctness is
more important than maximum throughput.

### Memory Management

MBL uses a function-scoped memory management system designed to optimize for
typical business application patterns:

**Function Instance Records:**
- Each function call creates an associated record as its data scope
- The system maintains averages of memory usage patterns for each function type
- Memory is pre-allocated based on historical usage to minimize reallocations
- Function scopes are garbage collected when the function completes and no
references remain

**Optimization Strategy:**
- Keep frequently-used function templates in memory
- Pre-allocate record space based on statistical usage patterns
- Minimize memory fragmentation through predictive allocation
- Balance memory efficiency with execution speed

### Tools

A tool is run from the console and accepts command line parameters.  An example
follows:

```mbl
tool concat_files( infile, outfile ):
    computer.file( outfile ) =+ computer.file( infile )
```

In the above example, the computer object is MBL's way of accessing resources
outside of itself, such as files (and anything else accessible through its
hosting computer operating system).

A tool would be run by calling it with MBL, as follows:

```bash
mbl concat_files.mbl firstfile secondfile
```

### Server

A server is started and runs in the background.  It can accept run-time
modifications.  The idea is for perpetual operation.  Downtime should be
avoided as much as possible -- whether unplanned or planned.

```mbl
server personnel( port=8080 ):
    let employees = computer.file( "employees.json" )

    webservice get_profile( username ):
        return employees[ username ]

    webservice modify_profile( username, attribute, value ):
        employees[ username ][attribute] = value
        return { result:"successful" }

    trigger vacation_time_expiring( employee ) when ( employee.vacation_time <=
8 ):
        send_notification(employee.email, "Low vacation time warning")
```

The above server provides two web service functions and one trigger function.
To start, check status, and stop the server, one would use the following
command from the console:

```bash
mbl start personnel.mbl  # .mbl extension is optional
mbl status personnel
mbl stop personnel
```

Once the service is operational, all services are enabled by default and the
following commands are available.

```bash
mbl put personnel webservice.mbl  # again, the .mbl extension is optional
mbl get personnel modify_profile  # returns source code of function
mbl del personnel vacation_time_expiring
mbl enable personnel modify_profile
mbl disable personnel get_profile
```

The put operation will add the function defined in the webservice.mbl file else
replace it, if pre-existing.

## Module System

MBL uses an automatic module loading system designed to minimize developer
overhead:

**Module Discovery:**
- Each server maintains a standard `modules/` directory
- When a function is referenced but not found in the current scope, the
interpreter automatically searches for a file named `{function_name}.mbl` in the
modules directory
- Modules are loaded automatically without explicit import statements

**Module Structure:**
- A module is simply an MBL file containing a single function definition
- The function name must match the filename (without extension)
- Functions, triggers, webservices, and constraints are all considered
"functions" for module purposes

**Example Module Structure:**
```
myserver.mbl
modules/
  validate_email.mbl
  format_currency.mbl
  send_notification.mbl
```

**Usage:**
```mbl
server myapp():
    webservice register_user(email, name):
        if validate_email(email):  # Automatically loads
modules/validate_email.mbl
            # process registration
            return { status: "success" }
        else:
            return { status: "error", message: "Invalid email" }
```

This approach eliminates the need for explicit import/require statements while
maintaining clear code organization.

## Scoping Rules

MBL uses function-based scoping with explicit access to parent scopes:

**Variable Scope:**
- Variables are scoped to the function in which they are declared
- Each function maintains its own record containing all declared variables as
attributes
- Variables are hoisted within their function scope (similar to JavaScript's
`var` hoisting)
- All variables must be explicitly declared using the `let` keyword

**Super Scope Access:**
- Functions defined within other functions can access the parent function's
scope using the `super` keyword
- `super.variableName` explicitly references a variable in the parent function
- This provides controlled access to parent scopes without automatic inheritance

**Example:**
```mbl
function outer():
    let x = 10
    let y = 20

    function inner():
        let x = 5  # shadows outer x
        let z = super.x + x  # z = 15 (10 + 5)
        super.y = 30  # modifies outer y
        return z

    return inner()
```

**Scoping Rules:**
1. Variables must be declared with `let` before use
2. Undeclared variables result in compilation errors
3. Variable lookup follows standard lexical scoping within the current function
4. Parent scope access requires explicit `super.` prefix
5. Global scope is not automatically accessible (use `computer` record for
global state)

## Assignment and Append Operators

MBL provides specialized assignment operators for common business data
manipulation patterns:

**Standard Assignment:**
- `=` : Replace the entire value
- `x = 5` replaces x with 5

**Append Operators:**
- `=+` : Append to the end (suffix append)
- `+=` : Prepend to the beginning (prefix append)

**Behavior by Data Type:**

**Text:**
```mbl
let message = "Hello"
message =+ " World"  # message becomes "Hello World"
message += "Hi "     # message becomes "Hi Hello World"
```

**Lists:**
```mbl
let items = [1, 2, 3]
items =+ [4, 5]      # items becomes [1, 2, 3, 4, 5]
items += [0]         # items becomes [0, 1, 2, 3, 4, 5]
```

**Numbers:**
```mbl
let total = 100
total =+ 25          # total becomes 125 (add after evaluation)
total += 10          # total becomes 135 (add before evaluation context)
```

**Files (via computer.file):**
```mbl
computer.file("log.txt") =+ "New log entry\n"  # append to end of file
computer.file("header.txt") += "Title: "       # prepend to beginning of file
```

The distinction between `=+` and `+=` for numbers is contextual - `=+` adds the
value after the right-hand expression is fully evaluated, while `+=` adds before
evaluation in complex expressions.

## Operator Precedence

MBL follows standard mathematical and programming operator precedence:

**Precedence Table (highest to lowest):**
1. **Parentheses**: `()`
2. **Member Access**: `.` (dot notation), `[]` (bracket notation)
3. **Function Calls**: `function()`
4. **Unary Operators**: `+`, `-`, `NOT`
5. **Multiplication/Division**: `*`, `/`, `%`
6. **Addition/Subtraction**: `+`, `-`
7. **Comparison**: `<`, `<=`, `>`, `>=`
8. **Equality**: `=`, `!=` (in conditional contexts)
9. **Logical AND**: `AND`
10. **Logical OR**: `OR`
11. **Assignment**: `=`, `=+`, `+=`

**Associativity:**
- Most operators are left-associative
- Assignment operators are right-associative
- Comparison operators are non-associative (chaining requires explicit
parentheses)

**Method Chaining:**
Method calls can be chained using dot notation, similar to JavaScript:
```mbl
let result = text.slice(0, 10).uppercase().trim()
```

## Expression Parsing

**Parentheses:**
Standard mathematical parentheses for grouping expressions:
```mbl
let result = (a + b) * (c - d)
```

**Method Chaining:**
Dot notation for accessing properties and calling methods:
```mbl
let formatted = employee.name.titlecase().slice(0, 20)
let data = computer.file("data.json").parse().records[0]
```

**String Interpolation with .form():**
The `.form()` method provides string interpolation capabilities:

**Default Behavior (current scope):**
```mbl
let name = "Alice"
let age = 30
let message = "Hello {name}, you are {age} years old".form()
# Result: "Hello Alice, you are 30 years old"
```

**With Explicit Record:**
```mbl
let person = { name: "Bob", age: 25 }
let message = "Hello {name}, you are {age} years old".form(person)
# Result: "Hello Bob, you are 25 years old"
```

**Custom Delimiters:**
```mbl
let message = "Hello <n>, you are <age>".form(person, "<", ">")
```

## Variable Declaration

**Declaration Requirements:**
- All variables must be declared using the `let` keyword
- Undeclared variables result in compilation errors (prevents typos)
- Variables are hoisted within their function scope

**Declaration Syntax:**
```mbl
let name              # declares name as nothing
let age = 25          # declares and initializes
let items = []        # declares empty list
let person = {}       # declares empty record
```

**Hoisting Behavior:**
Similar to JavaScript's `var` hoisting, but stricter:
```mbl
function example():
    # This works due to hoisting
    x = 10
    let x  # declaration is hoisted to top of function

    # This fails - y is never declared
    y = 20  # Compilation error: undeclared variable 'y'
```

**Function Scope Record:**
Each function's scope is implemented as a single record where all declared
variables become attributes:
```mbl
function example():
    let name = "Alice"
    let age = 30
    # Internally, this creates a record: { name: "Alice", age: 30 }
```

## Computer Record

The computer record provides access to system resources and capabilities.  It
is the primary access to everything outside of an MBL program.

It should include the following methods (among others):

### File Operations

```mbl
let myfile = computer.file( path )
let created = myfile.created
let line = myfile.until( newline )
let cursor = myfile.position
let myblock = myfile.slice( 100, 150 )  # 100 is position; 150 is length
myfile.splice( 100, 16, "Replacement text" ) # 100 is position; 16 is length
myfile.remove()
```

### Console Operations

```mbl
computer.write( "message to stdout")
computer.error( "message to stderr" )
computer.wait()  # flushes stdin buffer
let stdin = computer.read( until = newline )
```

### System Information

```mbl
let mytime = computer.time
let mytimezone = computer.timezone
let path = computer.variable("path")
```

### Network Operations

```mbl
let response = computer.http_get(url)
let response = computer.http_post(url, data)
```

### Database Operations

```mbl
let mydb = computer.odbc_connect(connection_string)
mydb.db_query(connection, query)
mydb.db_execute(connection, command)
```

Cursors and commits should be handled automatically.  This is to reduce work
for the developer.

## Type Coercion Rules

MBL employs aggressive type coercion to minimize developer effort and make
operations "just work" in intuitive ways:

**General Philosophy:**
- Coerce whenever a reasonable interpretation exists
- Prioritize business-friendly interpretations over strict type safety
- When multiple interpretations are possible, choose the most commonly needed in
business contexts

**Coercion Hierarchy:**
1. **Text**: Most permissive - can represent any value
2. **Number**: Flexible parsing from text, dates, money
3. **Boolean**: Flexible truthiness evaluation
4. **Time**: Parse from text and numbers
5. **Money**: Parse from text and numbers

**Common Coercion Rules:**

**Text Coercion:**
```mbl
let result = 3 + "4"        # "34" (number becomes text)
let result = "Price: " + $5 # "Price: $5.00"
let result = "Date: " + @2025-01-01  # "Date: 2025-01-01"
```

**Number Coercion:**
```mbl
let result = "123" + 456    # 579 (text becomes number)
let result = "12.5" * 2     # 25.0
let result = @2025-01-01 - @2024-01-01  # 365 (days difference)
```

**Boolean Coercion:**
```mbl
if "hello":     # true (non-empty text)
if "":          # false (empty text)
if 0:           # false
if 42:          # true
if []:          # false (empty list)
if [1,2]:       # true (non-empty list)
```

**Money and Time:**
```mbl
let amount = "$123.45" + "$56.78"    # $180.23
let date = "2025-01-01" + 30 days    # @2025-01-31
```

**Error Handling:**
When coercion is impossible, return an Unknown value with appropriate reason:
```mbl
let result = "abc" * 5  # Unknown{reason: "Cannot convert 'abc' to number"}
```

## Error Handling

Errors return an Unknown value with the error message in the Unknown value's
reason attribute.  Any function with an error should return this.

However, if multiple potentially correct values can be determined then they may
be returned in the Unknown value's possibles list attribute.

```mbl
let myvalue = get_my_value( 42, "blah" )
if myvalue = unknown:
    computer.error( unknown.reason )
    for possible myvalue.possibles:
        computer.error( "Possible value: " + possible )
else:
    computer.write( "Result: " + myvalue )
```

### Unknown Type

The Unknown type is used to represent both errors and undefined states in
ternary logic. It has the following properties:
- .reason: Text description of why the value is unknown
- .possibles: List of possible values that could resolve the unknown

In ternary logic operations:
- True AND Unknown = Unknown
- False AND Unknown = False
- True OR Unknown = True
- False OR Unknown = Unknown
- NOT Unknown = Unknown

Example ternary logic:
```mbl
function validate_age(age):
    if age < 0:
        return false
    if age > 150:
        return unknown("Age exceeds reasonable maximum")
    return true

# Ternary logic examples
result1 = validate_age(25) AND validate_age(200)  # Returns Unknown
result2 = validate_age(-1) OR validate_age(200)   # Returns False
result3 = validate_age(25) OR validate_age(200)   # Returns True
result4 = NOT validate_age(200)                   # Returns Unknown
```

When an Unknown value is used in a condition:
```mbl
if validate_age(200):
    # This block won't execute because Unknown is not True
    computer.write("Valid age")
elif validate_age(200).reason:
    # This block will execute
    computer.write("Age validation failed: " + validate_age(200).reason)
else:
    # This block won't execute because Unknown is not False
    computer.write("Invalid age")
```

Example error handling with ternary logic:
```mbl
function divide(a, b):
    if b == 0:
        return unknown("Division by zero")
    return a / b

result = divide(10, 0)
if result.reason:
    computer.write("Error: " + result.reason)
else:
    computer.write("Result: " + result)
```

## Comments

A comment is initiated with any number of adjacent "#" symbols (unless in a
string literal) and ends with the same number of adjacent "#"
symbols.  Consequently, comments may be recursive.  However, a comment starting
with a single # maybe terminated by the next single # but otherwise will
terminate at the end of the same line.  The single # comments allow for
multiple single line comments on the same line.

Example:
```mbl
# Comment ending at the end of the line
# Single-line comment # followed by not comment
## Multi-line
comment ##
### Nested
# comment
inside ###
```

## Data Value Types

- Nothing.  This is the value any non-assigned variable returns.  Assigning
nothing also destroys a variable.
- Anything.  Any value will match this and affects of anything, such as in
arithmetic, allow the MBL interpreter to select a value conforming to the need.
- Unknown.  Used for ternary operations.  An unknown may have the .reason (text
description) and .possibles (list) attributes.
- Boolean.  True or False.
- Number.  High precision floating point value.  Literal may include one decimal
and any number of underscores within (but not prefixed or suffixed).  The
underscores are purely for visual clarity purposes.
- Text.  UTF-8.  Literal strings begin with one or more adjacent quotes and end
with the same number of adjacent quotes.  There are no escapes.
- Time.  Has properties Year, Month, Day, Hour, Minute, and Second.  Literal
begins with "@" symbol in forms:  @YYYY-MM-DD, or @HH:MM:SS, or combined
@YYYY-MM-DD HH:MM:SS.
- Money.  Stored as integer with four digits below lowest denomination (e.g. the
penny).  Literal begins with "$" symbol with decimal after base denomination
(e.g. dollar).  The currency is USD by default but may be explicitly specified
suffixed to value (e.g. $19.95 USD).
- List.  A collection of values indexed numerically.  Literal representation is
in the form [ value1, value2, .. ]
- Record.  A collection of values indexed by name.  Literal form is myvar =
{ attrib1:value1, attrib2:value2, .. }
- function.  A sequence of instruction tokens with associated record as its
data scope.
- trigger.  A sequence of condition tokens with associated data scope and
associated function.

### Text

Text is UTF-8 characters and includes the following useful methods:

- .length()
- .slice( index, length )
- .splice( index, length, value )
- .uppercase()
- .lowercase()
- .titlecase()
- .escaped()
- .unescaped()
- .form( record, opener, closer )  -- this interpolates values into the string;

by default, the record would be the current variable scope, the opener is "{"
and the closer is "}".

Similar to a list, the characters of a text value may be retrieved by numerical
index.  For example:  `"Hello".slice(2,2)` provides "ll".

### Money

```mbl
$.USD.base = "dollar"
$.USD.lowest = "cent"
$.USD.dollar = 100
```

USD is the default currency (assumed if not specified).  It is defined above.
The base currency is what is meant when you write `$1 USD`. And $1 is equal to
100 cents.  In memory, for calculation purposes, the precision stored is to
four digits lower than the lowest denomination.

Exchange rates in other currencies may be specified in terms of USD's lowest
denomination.  The following is an example for the Korean WON.

```mbl
$.WON.base = "cheon"
$.WON.lowest = "shib"
$.WON.cheon = 100
$.WON.exchange = 100
```

In the above, 100 shib WON translate to 1 cent USD.  This is established by the
`$.WON.exchange = 100` as the exchange rates means how many USD base equate to
the WON's base.  Of course, WON here is an example of a currency.  The only
default currency is USD (which is why it's the basis for currency exchange
rates).

### Time

Time is held as a collection of the following attributes.

- years
- months
- days
- hours
- minutes
- seconds
- milliseconds

Not all need be specified but when adding or subtracting time, the attributes
not specified are ignored.  They will be unknown{reason:"not specified"}

```mbl
birth_date = @1970-07-29
birth_date = 1970 years + 7 months + 29 days
```

The above illustrates two ways of specifying the same date.  The first is the
short form and the second way is actually just adding durations of time
together.

In arithmetic, no sign prefixing a time attributes implies addition while a "-"
sign would indicate subtraction.

The `new_date = @2025-05-01 + 7 days + 8 hours` code would equate to
`@2025-05-08 08:00:00.0`.

As for days of the week, there is the following syntax:

```mbl
meeting_date = business thursday before @2025-08-15
meeting_date = business tuesday after @2025-08-15
```

prefixing a time expression with the keyword "business" will ensure that the
time fits within business hours.  Business hours are defined in the @business
list, as shown below.

```mbl
@business = [
    { open:@2025-01-01 08:00, close:@2025-01-01 17:00 },
    ..
]
```

### List

A list is numerically indexed (integers), dynamically sized, and may hold
different values.

The following assigns a new list to the mylist variable:
`mylist = ["text",3.14,@2025-03-06,$13.95 USD, [1,2,3], {name:"joe",
age:54}]`

Note that, although tab indentation after a colon is used to identify a code
block in MBL, the spacing, newlines, and tabs within an explicit list are
separate from this and may be used free-form.

Extracting the second item, 3.14, is done by writing `mylist[1]` because
indexes are zero-based.

Useful methods of a list include:

- .length()
- .slice( index, length )
- .splice( index, length, value(s) )

### Record

A record is name indexed, dynamically sized, and may hold different values.
The name used for each attribute within a record may be any text but following
variable name conventions allows the use of dot notation when referencing them.

```mbl
person = {
    name:"Joe",
    age:34
    "full-name":"Joe Broe"
}
```

In the above, we don't need quotes around the attribute names "name" or "age"
but we do around "full-name" because that name does not comply with the
variable name convention.  Note that, there is no possibility of keyword
conflicts in the definition of a record so using keywords here is allowed.

Referencing an attribute may be specified in the form `person["name"]` or
`person.name` or `person["full-name"]` but not `person.full-name`.  This is
similar to Javascript.

Note that, although tab indentation after a colon is used to identify a code
block in MBL, the spacing, newlines, and tabs within an explicit record are
separate from this and may be used free-form.

Also, a new record may inherit a base record by prefixing it with a base
record, such as this: `person = animal { name:"joe", age:34 }`.  In this case,
whatever the record "animal" is is merely extended in the new record "person".
The person is an animal.

### Function

A function is a code-block, optionally with a parameter list, that when
called, has a record associated with it to be its local data scope.  If the
function is not given an explicit return value then the entire record is
returned with it.

```mbl
calc( a, operation, b ):
    Consider operation:
        When "+": return a + b
        When "-": return a - b
        Otherwise: return unknown("{operation} unsupported".form() )
```

For a function inside a function to reach the data scope of the super-function,
there is the "super" keyword.

For a function to be extended by another function, merely prefix the base
function to the new function.  Let's say you have function "mybase" that you
want to use as a base-class for an "mynew" function:

```mbl
mybase( a, b ):
    # do stuff #

mybase mynew( a, b, c ):
    super(a,b)
    # do more stuff #
```

### Trigger

A trigger is a function that, instead of parameters, has a condition and
operates within the scope of its containing function. Triggers exist within the
scope of the function they are declared in and can access variables from that
scope.

```mbl
server inventory_manager():
    let stock_level = 100
    let reorder_point = 20

    trigger low_stock_alert( stock_level ) when ( stock_level < reorder_point ):
        send_notification("Stock level low: " + stock_level)
        initiate_reorder()
```

**Trigger Execution Model:**
MBL operates in moments of 1/3 second intervals. The execution model works as
follows:

1. All regular code executes normally, making variable assignments as needed
2. The system tracks which variables are referenced in trigger conditions
3. When a watched variable is assigned a new value, it's marked as "changed" for
the current moment
4. At the end of each moment, the system:
   - Collects all triggers whose watched variables changed during that moment
   - Evaluates each affected trigger's condition exactly once
   - Executes trigger actions for conditions that evaluate to true
   - Resets all "changed" flags for the next moment

**Trigger Assignment Rules:**
- Assignments made within triggers do not activate other triggers in the current
moment
- Such assignments may activate triggers in the next moment if conditions are
met
- This prevents cascading trigger execution and maintains system stability

**Trigger Conflict Resolution:**
When multiple triggers assign different values to the same variable in the same
moment, the memory manager creates a conflict resolution:

```mbl
# If two triggers assign different values to the same variable
trigger price_discount( product ) when ( product.category = "clearance" ):
    product.price = $45.00

trigger bulk_discount( product ) when ( product.quantity > 100 ):
    product.price = $72.00

# If both conditions are true in the same moment:
# product.price becomes:
unknown{
    reason: "trigger conflict",
    possibles: [
        { value: $45.00, source: "price_discount" },
        { value: $72.00, source: "bulk_discount" }
    ]
}
```

**Conflict Resolution Logic:**
Developers can write logic to handle trigger conflicts intelligently:

```mbl
function resolve_price_conflicts():
    if product.price = unknown and product.price.reason = "trigger conflict":
        # Business rule: customer gets the best deal
        let best_price = min(product.price.possibles[*].value)
        let winning_source = product.price.possibles.find(p => p.value =
best_price).source

        product.price = best_price
        log_price_decision("Applied {winning_source}: {best_price}")
```

This batched evaluation ensures triggers see a consistent state reflecting all
changes made in the moment, rather than intermediate states. It also prevents
cascading or thrashing behavior that could occur if triggers were evaluated
immediately upon every variable change.

### Constraint

A constraint is similar to a trigger but evaluates immediately when a variable
changes rather than at the end of a moment. It is used to enforce business rules
and data validation. Unlike triggers, which are used for reactions to data
changes, constraints are used to prevent invalid data from being stored in the
first place.

Constraints include an optional healing action that can automatically correct
invalid data, rather than simply rejecting it.

```mbl
constrain( x < 20 ):
    # If x is assigned a value >= 20, the assignment will fail
    # The constraint validation happens immediately on assignment

constrain( x < 20 ):
    # This constraint includes a healing action
    x = 20  # If x would exceed 20, cap it at 20 instead
```

The execution model for constraints works as follows:

1. The system tracks which variables are referenced in constraint conditions
2. When a watched variable is assigned a new value:
   - All constraints that reference this variable are immediately evaluated
   - If any constraint evaluates to false (condition violated):
     - If the constraint has a healing action, it's executed to try to fix the
data
     - If healing succeeds (constraint now evaluates to true), the assignment
proceeds
     - If healing fails or there is no healing action, the assignment is
rejected
   - If all constraints pass, the assignment proceeds normally

Constraints provide immediate validation and self-healing capabilities,
complementing the moment-based trigger system for a complete reactive
programming model.

## Conditions

Conditions are context sensitive.  So outside of a condition, for example, "="
is for assignments but inside a condition, it is for evaluating equality.

```mbl
if x = 5: computer.write("It's five!") # single line
if x = 6: computer.write("It's six") # if and also else each on single lines
else: computer.write("It's not six")
if x = 7:
    computer.write("It's seven")
    computer.write("Truly it is.")
else:
    let diff = 7 - x
    computer.write("It's {x} different from seven".form())
```

## Loops

```mbl
let x = 1
while( x < 10 ):
    computer.write("Counting to {x}".form())

fruits = ["apples","oranges","pears"]
for fruit in fruits:
    computer.write("We have yummy {fruit}".form())

profile = { name:"Matthew", age:54, balance:$124.52 }
for attrib in profile:
    computer.write("{attrib} is {profile[attrib]}".form())
```

## Technical Implementation

### Architecture Overview

MBL implementation uses a minimal file structure in Zig with five core
components:

```
src/
├── main.zig          # MBL command-line interface
├── memory.zig        # Memory manager with conflict resolution
├── lexer.zig         # Tokenization and source code parsing
├── parser.zig        # Grammar parsing and AST generation
└── runtime.zig       # Execution engine and integration
```

### Component Descriptions

**main.zig (MBL Command Interface)**
- Handles command-line argument parsing
- Manages tool vs server execution modes
- Implements server lifecycle commands (start, stop, status)
- Interfaces with runtime for execution
- Minimal CLI focused on MBL-specific operations

**memory.zig (Memory Manager)**
- Function-scoped record management
- Variable conflict detection and resolution
- Moment-based trigger coordination
- Garbage collection and memory optimization
- Core data type implementations (Text, Money, Time, etc.)
- Unknown value creation and management

**lexer.zig (Lexer/Tokenizer)**
- Source code tokenization
- Comment handling (single and multi-level)
- String literal parsing (multi-quote support)
- Number, money, and time literal recognition
- Operator and keyword identification

**parser.zig (Parser and Grammar)**
- Recursive descent parser
- AST generation from tokens
- Grammar validation and error reporting
- Scope analysis and variable declaration tracking
- Expression precedence handling

**runtime.zig (Runtime Engine)**
- AST execution and interpretation
- Integration of memory, lexer, and parser
- Built-in function implementations
- Module loading and management
- Trigger and constraint evaluation
- Type coercion and operation handling

### Grammar Specification

```ebnf
program = ( tool_def | server_def )

tool_def = "tool" identifier "(" param_list? ")" ":" block

server_def = "server" identifier "(" param_list? ")" ":" block

function_def = identifier "(" param_list? ")" ":" block

webservice_def = "webservice" identifier "(" param_list? ")" ":" block

trigger_def = "trigger" identifier "(" param_list ")" "when" "(" expression ")"
":" block

constraint_def = "constrain" "(" expression ")" ":" block?

param_list = identifier ( "," identifier )*

block = ( statement | function_def | webservice_def | trigger_def |
constraint_def )*

statement = ( assignment | if_stmt | while_stmt | for_stmt | return_stmt |
expression_stmt )

assignment = identifier ( "=" | "=+" | "+=" ) expression

if_stmt = "if" expression ":" ( statement | block ) ( "else" ":" ( statement |
block ) )?

while_stmt = "while" "(" expression ")" ":" block

for_stmt = "for" identifier "in" expression ":" block

return_stmt = "return" expression?

expression_stmt = expression

expression = or_expr

or_expr = and_expr ( "OR" and_expr )*

and_expr = equality_expr ( "AND" equality_expr )*

equality_expr = comparison_expr ( ( "=" | "!=" ) comparison_expr )*

comparison_expr = addition_expr ( ( "<" | "<=" | ">" | ">=" ) addition_expr )*

addition_expr = multiplication_expr ( ( "+" | "-" ) multiplication_expr )*

multiplication_expr = unary_expr ( ( "*" | "/" | "%" ) unary_expr )*

unary_expr = ( "+" | "-" | "NOT" )? postfix_expr

postfix_expr = primary_expr ( "." identifier | "[" expression "]" | "("
arg_list? ")" )*

primary_expr = ( identifier | literal | "(" expression ")" | list_literal |
record_literal )

literal = ( number | text | time | money | boolean )

list_literal = "[" ( expression ( "," expression )* )? "]"

record_literal = "{" ( record_field ( "," record_field )* )? "}"

record_field = ( identifier | text ) ":" expression

arg_list = expression ( "," expression )*

identifier = [a-zA-Z_][a-zA-Z0-9_]*

number = [0-9]+ ( "." [0-9]+ )?

text = quote+ [^quote]* quote+

time = "@" ( date | time_part | date " " time_part )

money = "$" number ( " " currency )?

boolean = "true" | "false"
```

### Memory Manager Design

**Core Structures:**
- Variable records with conflict tracking
- Moment-based change detection
- Trigger dependency graphs
- Type-specific memory pools

**Conflict Resolution Algorithm:**
1. Track all assignments to variables during moment
2. Detect conflicts when multiple sources assign to same variable
3. Create Unknown value with reason and source-attributed possibles
4. Provide conflict metadata for intelligent resolution

**Memory Optimization:**
- Pre-allocate function scopes based on usage patterns
- Pool common data types (Text, Number, Money)
- Predictive allocation for recursive function calls
- Efficient garbage collection of unused scopes
